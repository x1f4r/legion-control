# Legion Control agent contract, version 3

The wire between the clients and the agent. One JSON object per invocation over
ssh, no daemon, no open port.

This file is normative. Where it disagrees with a client or with the agent, this
file is right and the code is a bug — with one exception, stated in
[section 14](#14-fixtures-and-vectors): if a fixture or a vector disagrees with
this prose, the fixture or vector wins, because they are what every
implementation is tested against.

- Schemas: `contract/schemas/*.schema.json`
- Fixtures: `contract/fixtures/`, listed in `contract/fixtures/index.json`
- Canonical hash vectors: `contract/hash-vectors.json`
- Conformance vectors: `contract/vectors/index.json`, which also lists `contract/hash-vectors.json`
- Check everything: `node contract/validate.mjs`
- Regenerate or check generated files: `node contract/tools/generate.mjs [--check]`

## 1. Compatibility rules

Read these first. Everything else assumes them.

1. Every reply from a 3.x agent carries `"contract": 3` and `"agentVersion":
   "3.x.y"`. Clients gate every v3 feature on `contract >= 3` and nothing else.
2. The absence of `contract` means a 2.x or 1.x agent. Such a client keeps the
   existing key-sniffing paths (`services`, `controller`, `bootTargets`) and
   offers the agent install action. There is no other way to detect a 2.x agent
   and no capability probe is needed.
3. A 3.x agent answers every 2.x command with the 2.x shape plus additive keys.
   `update` without `--service` still selects the first service. The legacy
   `t3`, `pendingRestart`, `lastUpdate` and `connect` top-level keys stay in
   `status` throughout contract 3 and are removed in contract 4.
4. **Keys are only ever added, never renamed and never retyped.** A client
   decodes with every field optional and ignores keys it does not know. The
   schemas here are strict about what the agent may *produce*; a client must be
   lenient about what it *accepts*. Those are different jobs and the asymmetry is
   deliberate.
5. Serialise every argv for the system's grammar exactly as
   [section 15](#15-command-lines-and-retry-safety) specifies. A system
   restricted on the route uses the dispatcher grammar on every platform.
   Generic non-path arguments match

   ```
   ^[A-Za-z0-9][A-Za-z0-9._:@/\\~=+-]*$
   ```

   Paths may contain spaces and quotes; unrestricted `--from` is a path option.
   Service, action and configured boot-target ids instead match
   `^[A-Za-z0-9][A-Za-z0-9._-]*$`. Setup ids match
   `^[A-Za-z0-9][A-Za-z0-9._:-]{0,63}$`; operation ids match
   `^[a-z0-9-]{8,64}$`. The shared document's machine, site and endpoint ids retain
   their existing token grammar; they are not agent service identifiers. Every
   pattern in this contract matches the whole input (`\A…\z` in .NET and ICU,
   `Regex.matches()` in Kotlin, `^…$` with the `u` flag in JavaScript) with
   ASCII classes only, never `\d`, and a value holding U+000A or U+000D is
   refused before any pattern is applied.
6. `reasonCode` is a closed enum ([section 3](#3-reasoncode)). Clients render by
   code and fall back to `message`. Codes may be added in a later 3.x; a client
   that meets an unknown one treats the reply as "failed, show the message".
7. Exit code 0 when the command did what was asked, 1 otherwise. `accepted`,
   `already-running`, `deferred`, `queued`, `noop` and `conflict` are exit 0 and
   `ok: true`.
8. `status`, `busy`, `op`, `history`, `logs`, `doctor`, `bundle`, `config`
   (read), `policy` (read), `version` and `help` never mutate the machine.
   `status` may write only the reconstructible cache file.
9. A client that reads a `contract` greater than the highest it implements
   keeps using the highest it implements and says once that the app is older
   than the agent. Nothing else tells a client it is too old, and nothing needs
   to: keys are only added (rule 4), an unknown `reasonCode` falls back to
   `message` (rule 6), and unknown document keys are preserved
   ([section 9.6](#96-unknown-keys)).

### There is no legacy dialect

Some early client work invented a "2.x dialect" — `--operation`, `operation
get`, `log`, `queue`, `pause`, `window`, `update --all`. **None of it ever
existed.** Agent 2.1.0 has `status`, `busy`, `update`, `restart`, `boot`,
`sleep`, `run`, `auto-update`, `config`, `config set`, `version` and `help`, and
no durable operations, policy, queue or doctor at all. Do not implement, send or
decode any of those verbs. A client talking to a 2.x agent uses the 2.x commands
above with their real 2.x behaviour, and everything in this document that a 2.x
agent cannot do is simply unavailable, with a reason the user can read.

### Capabilities

`contract >= 3` gates the whole v3 command surface. There is no capability
negotiation and no capability name may be required to unlock a verb.

`status.agent` and `version` may carry a `capabilities` array. It is
**documentation of optional behaviour**, never a gate. The frozen names:

| name | means |
| --- | --- |
| `setup-lineage` | the agent enforces the ancestry rules of [section 9](#9-the-shared-setup-and-its-lineage). Implied by `contract >= 3`. |
| `wol-action` | the agent can send wake-on-LAN packets itself (`actions[].kind == "wol"`). Discoverable from `status.actions` and not needed as a name. |
| `configured-telemetry` | explicit agent-local probes can add the optional `status.metrics` array. No probes means no collection. |
| `service-config-admin` | an unrestricted session can read, validate and save machine-local configuration with `service-config`. Restricted sessions are refused. |

A client that wants to know whether an action can wake a machine reads
`status.actions[].kind`. A client that wants to know whether lineage is enforced
reads `contract`. Neither asks for a capability list.

### Additions in agent 3.1.0

Contract stays 3. Agent 3.1.0 adds keys and brings its replies in line with the
fixtures. A client recognises each addition by its presence, never by comparing
versions:

| addition | when absent |
| --- | --- |
| `outcome` (5.6) | reduce it with the function in 5.6 |
| `config` `raw` (4, 9.5) | rebuild, adopt only on a matching hash, otherwise decline |
| `status.agent.floor`, self-update `floor` (13) | no downgrade protection; never send `--allow-downgrade` |
| `status.agent.signed` | unknown |
| `problems` on a `config set` refusal (9.4) | read `message` |
| `launchChanges` on a `restricted` `config set` refusal (9.4) | read `message` |

## 2. The reply envelope

On every reply from a 3.x agent, whatever the command and whatever went wrong.

```jsonc
{
  "ok": true,
  "contract": 3,
  "agentVersion": "3.0.0",
  "system": { "id": "linux", "name": "Raspberry Pi OS" },
  "reasonCode": "busy",     // only when the action was not the happy path
  "message": "human sentence",
  "notes": []               // warnings worth showing, optional
}
```

`ok`, `contract`, `agentVersion` and `system` are always present. Everything
else in this document is added on top of them.

## 3. reasonCode

The closed enum. Grouped for reading only.

| group | codes |
| --- | --- |
| busy gate | `busy`, `busy-unknown` |
| policy | `policy-off`, `policy-paused`, `outside-window` |
| exclusion | `operation-in-progress`, `lock-held` |
| updates | `no-update`, `latest-unknown`, `not-installed`, `not-running`, `app-closed`, `apply-attempts-exhausted`, `apply-failed`, `postcondition-failed`, `rolled-back` |
| configuration and platform | `not-configured`, `unsupported-platform`, `unknown-service`, `unknown-target`, `unknown-action`, `bad-argument`, `config-invalid`, `config-missing` |
| operation lifecycle | `interrupted`, `expired`, `cancelled`, `already-running`, `already-on-target` |
| setup documents | `stale-revision`, `controller-conflict` |
| trust and access | `signature-invalid`, `restricted` |
| generic | `timed-out`, `internal` |

`restricted` is only ever an authorisation denial for a restricted session: the
forced-command dispatcher refusing a command or shape, `service-config` refusing
every verb (section 8), `self-update` refusing a downgrade or a rollback below
the version floor (section 13), or `config set` refusing a launch value the
machine does not hold or a held copy it cannot read (section 9.4). A command or
flag the agent does not support is `bad-argument`, on a restricted session as
much as anywhere else, and a client that meets it stops sending that flag for
the rest of the session rather than trying another shape.

Every one of these codes is shown by at least one fixture; `contract/validate.mjs`
fails if one is not.

## 4. Command surface

New installs use `node <base>/bin/launcher.mjs <command> [args] [--flags]`.
The stable launcher survives replacement of `<base>/agent`. An existing direct
`node <base>/agent/src/index.mjs` command remains valid while the live tree exists.

| command | args and flags | mutates | summary |
| --- | --- | --- | --- |
| `status` | `--budget-ms N` (default 20000) | cache only | bounded snapshot with timing and partial flags |
| `busy` | `--budget-ms N` | no | aggregate busy plus per-service evidence |
| `update` | `--service ID`, `--force`, `--op ID`, `--detach`, `--when-idle`, `--expires DUR` | yes | manual update of one service |
| `restart` | `--service ID`, `--force`, `--op ID`, `--detach`, `--when-idle`, `--expires DUR` | yes | restart one service |
| `boot` | `TARGET`, `--force`, `--no-reboot`, `--op ID`, `--when-idle`, `--expires DUR` | yes | arm the next boot and reboot |
| `sleep` | `--force`, `--op ID`, `--when-idle`, `--expires DUR` | yes | suspend |
| `run` | `ACTION`, `--force`, `--op ID`, `--detach`, `--when-idle`, `--expires DUR` | yes | a configured action |
| `cycle` | `--op ID`, `--dry-run` | yes | the scheduled pass over every eligible service |
| `policy` | `--service ID`; `policy set [--service ID]` with a JSON patch on stdin | read / config | the effective update policy |
| `auto-update` | `on`\|`off` `[--service ID]`; `pause DUR` \| `resume` `[--service ID]` | config | the 2.x switches, answering in the v3 shape |
| `op` | `ID`, `--wait SECONDS` | no | one operation record; `--wait` long-polls |
| `cancel` | `ID` | ops | cancel a queued operation |
| `history` | `--limit N` (default 30, max 200), `--service ID`, `--kind K` | no | operation summaries, newest first |
| `logs` | `--lines N` (default 100, max 500), `--op ID` | no | the agent log, or one operation's log |
| `doctor` | `--service ID`, `--deep` | no | preflight and diagnosis |
| `bundle` | | no | doctor, status, history, logs and a redacted config in one reply |
| `config` | none; `set --controller-id ID --revision N [--replace]`; `meta` | setup copy | the stored setup document |
| `service-config` | `get`; `validate --stdin`; `set --stdin` | read / agent config | unrestricted administrative editor; no service commands execute |
| `self-update` | `--from PATH`, `--stdin`, `--install`, `--rollback`, `--check`, `--allow-downgrade` | agent tree | signed agent replacement |
| `dispatch` | | as dispatched | reads `SSH_ORIGINAL_COMMAND` in a restricted session |
| `version` | `--check` | no | who is answering; `--check` is the staged tree's self-test |
| `help` | | no | the command table |

`DUR` is `^[0-9]+(m|h|d)$`. Internal, never called by a client: `op-run ID`,
`op-run --queued`.

### Canonical reply keys

These were open questions during implementation. They are closed.

| command | the key to read | items |
| --- | --- | --- |
| `op ID` | `op` | the operation record. `id` and `waited` are additive; the record is always under `op`. An id with no record answers `ok: false`, `reasonCode: "not-configured"`, `op: null`. `cancel ID` and `logs --op ID` answer the same code in the refusal shape. A client treats a present `op: null` as "no record", whatever the code: 3.0.x agents send it with `bad-argument`. |
| `history` | `operations` | an `opSummary`; a whole record is also allowed and a client reads the summary fields out of either. Not `history`, not `items`. |
| `logs` | `lines` | `{ at, line }`, plus an optional `command`. `at` is null on a line with no timestamp prefix and `line` is then the whole line. |
| `config meta` | `meta` | `{ id, revision, updatedAt, source, lineage }` plus optional `device`, `hash`, `bytes`. |
| `config` | `raw`, `bytes` | `raw` is the stored document as text: exactly the canonical bytes ([section 12](#12-canonical-setup-bytes)) that `hash` covers, at most 1 MiB of UTF-8, null exactly when `controller` is null. `bytes` is the UTF-8 length of `raw`, 0 when it is null. `controller` is the same document parsed, kept for older clients. Hash and adopt `raw`; never re-serialise `controller`. A `config` reply is at most 4 MiB of stdout. |
| `policy` (machine) | `updates` and `services` | `services` is `[{ id, name?, updates }]`, so the whole maintenance screen comes from one call instead of one call per service. |
| `policy --service ID` | `updates` | the effective policy for that service; no `services` key. |
| `self-update` | `manifest` | the **internal** `agent/MANIFEST.json` summary, not the release-artifact manifest. |
| `service-config get` | `hash`, `document`, `templates`, `limits` | the complete local config and its opaque comparison token; never exposed to restricted sessions. |
| `service-config validate` / `set` | `valid`, `hash`, `proposedHash`, `changes`, `warnings` | validated service changes; successful set also reports `saved: true`. |

## 5. Operations

### 5.1 The record

Stored at `<base>/ops/<id>.json`, one file per operation, written to a unique
temp name and renamed. It is also what `op` returns under `op`, what every
mutating reply embeds under `op`, and what `history` and `status.operations`
summarise.

```jsonc
{
  "id": "6f1c2a84-…",
  "kind": "update",              // update | restart | boot | sleep | run | cycle | self-update
  "service": "t3",               // update/restart only; null otherwise
  "target": "windows",           // boot only; null otherwise
  "actionId": "sunshine-restart",// run only; null otherwise
  "mode": "manual",              // scheduled | manual | force | queued
  "initiator": { "client": "mac", "device": "…", "user": "…" },
  "state": "running",            // queued | running | finished
  "phase": "installing",
  "progress": { "step": 4, "of": 8, "note": "npm install …" },
  "requestedAt": "…", "startedAt": "…", "updatedAt": "…",
  "finishedAt": null,            // set exactly when state is finished
  "expiresAt": null,             // queued only
  "pid": 24817,                  // null when queued or finished
  "detached": true,
  "from": "0.0.36-…", "to": "0.0.37-…",
  "result": null,                // set exactly when state is finished
  "log": [ { "at": "…", "line": "stopped t3-code.service" } ],   // <= 200
  "children": [ … ],             // cycle only
  "agentVersion": "3.1.0",
  "systemId": "linux",
  "outcome": "pending"           // section 5.6, from agent 3.1.0
}
```

`result` is `{ ok, action, reasonCode, message, from?, to?, exitCode?, output?,
verified?, outcome? }`. `ok: true` carries `reasonCode: null`; `ok: false`
always carries a code. "It failed and we will not say why" is the answer
contract 3 exists to remove.

`initiator.client` comes from `LEGIONCTL_CLIENT`, which the restricted
dispatcher sets from the `authorized_keys` comment. A local shell is `"cli"`.

### 5.2 Phases

| kind | phases, in order |
| --- | --- |
| `update` | `resolving`, `recovering`, `checking-busy`, `warming`, `locking`, `stopping`, `installing`, `verifying`, `starting`, `health`, `rolling-back`, `done` |
| `restart` | `checking-busy`, `locking`, `restarting`, `health`, `done` |
| `boot` | `checking-busy`, `locking`, `arming`, `verifying`, `rebooting`, `done` |
| `sleep` | `checking-busy`, `locking`, `preparing`, `suspending`, `done` |
| `run` | `checking-busy`, `locking`, `running`, `done` |
| `cycle` | `recovering`, `queued`, `services`, `done` |
| `self-update` | `verifying`, `staging`, `self-test`, `swapping`, `done` |

A finished record is always in phase `done`.

### 5.3 Result actions

| kind | actions |
| --- | --- |
| `update` | `updated`, `noop`, `deferred`, `queued`, `failed`, `rolled-back`, `accepted`, `conflict`, `interrupted`, `cancelled`, `expired`, `already-running` |
| `restart` | `restarted`, `deferred`, `queued`, `failed`, `accepted`, `conflict`, `interrupted`, `cancelled`, `expired`, `already-running` |
| `boot` | `rebooting`, `rebooted`, `armed`, `noop`, `deferred`, `queued`, `failed`, `conflict`, `interrupted`, `cancelled`, `expired`, `already-running` |
| `sleep` | `sleeping`, `slept`, `deferred`, `queued`, `failed`, `conflict`, `interrupted`, `cancelled`, `expired`, `already-running` |
| `run` | `ran`, `deferred`, `queued`, `failed`, `accepted`, `conflict`, `interrupted`, `cancelled`, `expired`, `already-running` |
| `cycle` | `cycled`, `skipped`, `failed`, `conflict`, `already-running` |
| `self-update` | `installed`, `rolled-back`, `noop`, `checked`, `failed`, `conflict`, `accepted`, `already-running` |

`accepted` is the immediate answer to `--detach`: the work is running, and the
client polls `op ID --wait 20`. It is never a claim that anything finished.
`queued` is the answer to `--when-idle`.

### 5.4 The operation lock

One machine-wide lock, taken by every mutating command and by `cycle`, for the
whole operation. How it is held is the agent's business and is not part of this
contract — it names files under `<base>` and none of them are on the wire. What
IS part of this contract is the behaviour: mutual exclusion across processes,
release when the holding process dies, and never taking a lock away from a live
one. A second mutation while it is held answers
`action: "conflict"`, `reasonCode: "operation-in-progress"` (or `"lock-held"`
for `cycle`) with

```jsonc
"conflict": { "opId": "…", "kind": "update", "service": "t3", "phase": "installing", "startedAt": "…" }
```

so the app can name what is in the way instead of saying "busy". **`--force`
never breaks this lock.** `status`, `busy`, `doctor`, `op`, `history` and `logs`
do not take it.

A lock is released only when its owner is gone. **Age alone never makes a lock
stealable**, because the owner of a lock that is merely slow is a process in the
middle of stopping a service, and taking it away means two processes stopping
the same service at once.

### 5.5 Idempotency and recovery

A mutating command with `--op ID` whose record already exists returns that
record. While it is queued the action is `queued`. While it runs the action is
`already-running` (never `accepted`), with `ok: true`,
`reasonCode: "already-running"`, `replayed: true` and `detached` copied from the
record; a client follows it exactly as it follows `accepted`. A finished record
is returned as the finished result with `"replayed": true`. A client that lost
its link retries with the same id and can never start the work twice.

**An id binds its intent.** The same id with a different kind, service, target,
action, force or queue intent is a conflict, not a replay, and is refused with
`bad-argument` naming `--op`, never replayed and never reported as a lock
`conflict`.

Recovery runs at the start of every mutating command and of `cycle`, never in
`status`. Every record whose `state` is `running` and whose `pid` is dead is
finished as `interrupted`. For an interrupted update between `stopping` and
`starting`, recovery brings the service back up and, when the installed version
is neither `from` nor `to`, rolls back to `from`. This happens before any
registry or network lookup.

`rebooted` and `slept` are only ever written by recovery, and only on evidence:
the observed running system is the target, and the machine's boot identity says
it went down after the request. **Uptime alone is never evidence.** A dropped
connection is never evidence, even when the last reading was idle and even when
the request was forced. Only an acknowledgement, or a later observation,
establishes that a transition happened.

A recovery obligation clears only on a positive running reading or a successful
start; a failed or unreadable probe keeps it and says why.

### 5.6 Outcome

Every reply to a mutating invocation (`update`, `restart`, `boot`, `sleep`,
`run`, `cycle` without `--dry-run`, `cancel`, `config set`, `policy set`,
`auto-update`, `self-update` without `--check`, `service-config set`), every
operation record (`op.outcome`, and `result.outcome` once finished) and every
operation summary carries `outcome`:

| outcome | Meaning | Client action |
| --- | --- | --- |
| `succeeded` | finished; the requested state holds, including "it already did" | show success |
| `failed` | finished; not in effect, and the state is known | show the reason; a new attempt uses a new `--op` |
| `deferred` | finished without acting, by design | offer "later" (plus Force for `busy`/`busy-unknown`), with a new id |
| `pending` | the agent still owns the work | poll `op ID --wait 20`; a transport failure never changes this |
| `unknown` | no evidence either way | never resend; offer "check again" (same id, `op` read only) |

A queued or running record is always `pending`; a finished one never is. `ok`
keeps its meaning from rule 7 (replies) and section 5.1 (records); `outcome` is
the field a client decides on. When `outcome` is absent — agents before 3.1.0,
and 2.x replies — or holds a value the client does not know, the client reduces
it with this function, identically on every platform and tested against
`contract/vectors/outcome.json`. A record is reduced from
`{ ...op.result, state: op.state, outcome: op.outcome ?? op.result?.outcome }`;
`result` is null until the record is finished.

```
reduceOutcome(x):
 1. if x.outcome is a string:            return x.outcome ∈ OUTCOMES ? x.outcome : "unknown"
 2. if x.state ∈ {queued, running}:      return "pending"
 3. switch x.action:
    accepted | already-running | queued | rebooting | sleeping              → "pending"
    updated | restarted | ran | rebooted | slept | armed | installed |
      cycled | noop | checked | skipped | stored | replaced                 → "succeeded"
    deferred | conflict | expired                                           → "deferred"
    cancelled    → x.reasonCode == null ? "succeeded"
                   : x.reasonCode == "cancelled" ? "deferred"
                   : x.reasonCode == "internal" ? "unknown" : "failed"
    rolled-back  → x.reasonCode == null ? "succeeded" : "failed"
    interrupted  → "unknown"
    failed       → x.reasonCode ∈ {timed-out, interrupted} ? "unknown" : "failed"
    null/absent  → x.ok === true  ? (x.reasonCode == null ? "succeeded" : "unknown")
                   x.ok === false ? (x.reasonCode ∈ {operation-in-progress, lock-held} ? "deferred"
                                     : x.reasonCode ∈ {timed-out, interrupted, internal} ? "unknown" : "failed")
                   otherwise "unknown"
    any other string → "unknown"
```

The agent computes `outcome` with the same function, except that a producer
which knows a failed result may have changed the machine reports `unknown`. It
never reports anything more optimistic than the function. `pending` is followed
with `op ID --wait 20`, and a failed poll, a dropped link or a timeout never
turns it into anything else. `deferred`, `failed` and `succeeded` are terminal:
polling stops, and a new attempt is a new request with a new `--op` id.
Re-sending the same id is only for a request that may not have arrived.
`unknown` is never retried automatically; the client re-reads the same id and
leaves any new attempt to a person.

Reference implementation: `contract/tools/outcome.mjs`.

## 6. The busy gate

Per-service:

```jsonc
{ "busy": true, "unknown": false, "monitored": true, "reason": "1 turn running",
  "evidence": "t3-sqlite", "checkedAt": "…", "elapsedMs": 118, "error": null,
  "runningTurns": 1, "pendingTurns": 0, "pendingApprovals": 0,
  "staleTurns": 1, "staleApprovals": 0, "abandonedTurns": 0,
  "path": "…/userdata/statev2.sqlite", "threads": [ … ], "threadsTruncated": 0 }
```

`evidence` is `t3-sqlite | command | http | none | unmonitored | probe-error |
timed-out`.

**It fails closed everywhere.** `unknown: true` always implies `busy: true`.
There is no state in which the gate does not know and lets disruptive work
through.

Three states that must never blur into each other:

| situation | `monitored` | `unknown` | `busy` | `evidence` |
| --- | --- | --- | --- | --- |
| a probe ran | `true` | `false` | as read | the probe kind |
| the config says `busy.type: "none"` | `true` | `false` | `false` | `none` |
| no `busy` key at all | `false` | `true` | `true` | `unmonitored` |

A missing busy configuration is **unmonitored, not idle**. It blocks every
disruptive action until somebody says what busy means for that service, either
by configuring a probe or by declaring `{"type": "none"}`. An explicit `none` is
an answer, so it counts as monitored and nothing warns about it;
`status.busy.unmonitoredServices` is therefore the number of services that block
for want of a probe, which is a number a client can render as something to fix.

An unknown `busy.type`, a `command` probe with no argv and an `http` probe with
no port are `config-invalid`, never silently `none`.

A running turn never ages out on its timestamp alone. A `running` row is
abandoned only on independent evidence: the service process is not running, or
it started after the row was requested, because a turn cannot survive its
server's restart. `staleHours` applies to pending turns and approvals only. An
abandoned row does not block: `abandonedTurns` counts them, and their
`disposition` is `abandoned`. A `t3-sqlite` probe names the database it read, or
looked for, in `path`.

The busy gate is re-run after cache warming and lock acquisition and again
immediately before the service is stopped. A `busy` answer there releases the
lock and records `deferred`.

Aggregate: `{ busy, unknown, reason, monitoredServices, unmonitoredServices }`.
A machine with exactly one service answers `busy` in the 2.x shape — that
service's own object spread across the top level — and with several it sends the
aggregate plus a `services` array.

A machine with no services answers in the one-service shape: `busy: false`,
`unknown: false`, `monitored: true`, `evidence: "none"`,
`reason: "no services are configured"`, both counts 0.

A process probe whose `error` is non-null or whose `state` is `unknown` is not
evidence that the process stopped: no running turn is abandoned and the stop
guard holds.

## 7. Policy

The agent config's top-level `updates` replaces `autoUpdate`, which stays
readable and writable as an alias of `updates.automatic`.

```jsonc
"updates": {
  "automatic": true,
  "pauseUntil": null,
  "maintenanceWindows": [ { "days": ["mon","…"], "from": "02:00", "to": "06:00" } ]
}
```

Per service, `updates` with the same keys, where `null` inherits.

- **Scheduled** (`cycle`): eligible only when system automatic is on, not
  paused, inside a window, the service's inherited automatic is on and not
  paused, and the service is not busy. Otherwise the per-service outcome is
  `deferred` with the matching code.
- **Manual** (`update`, `restart`, `run`, `boot`, `sleep` from a client):
  ignores automatic, pause and windows **entirely**. It is busy-gated, and
  `--force` overrides the busy gate and nothing else — never the operation lock,
  never the configuration validity check, and never an unknown latest version.
- **Global `automatic: false` is a scheduler stop.** It does not disable the
  when-idle queue, does not disable manual requests, and does not disable setup
  replication between peers.

`policy set [--service ID]` reads a JSON patch from stdin. No positional
argument.

| in the patch | means |
| --- | --- |
| key absent | unchanged |
| `"pauseUntil": null` at a service | inherit from the machine |
| `"pauseUntil": null` at the machine | clear the pause |
| `"maintenanceWindows": null` at a service | inherit |
| `"maintenanceWindows": null` at the machine | clear to `[]`, which means any time |
| `"automatic": null` at a service | inherit |
| `"automatic": null` at the machine | invalid: the machine value must be a boolean |

The reply carries the **effective** policy after the patch, not the patch, so a
screen redraws from the answer rather than from what it hoped it did. `changed`
lists the keys actually rewritten; only touched keys are written.

`status` carries the effective policy under `updates`, the 2.x boolean under
`autoUpdate`, and per service `updates` with `inherited`, `eligibleNow` and
`deferredReason`. `updates.order` and `updates.after` are optional additive
ordering hints for the cycle; clients may ignore them.

## 8. Status

Bounded. Independent probes run concurrently, each with its own timeout; when
the budget is spent the rest are reported as `timed-out` and `timing.partial` is
true. **A status that came back inside its budget with some rows missing is
worth more than one that arrived after the client gave up**, but only because it
says which rows those were.

```jsonc
{
  "ok": true, "contract": 3, "agentVersion": "3.1.0", "system": {…},
  "os": "linux", "hostname": "beacon",
  "timing": { "budgetMs": 20000, "elapsedMs": 2310, "partial": false },
  "agent": { "version": "3.1.0", "contract": 3, "base": "…", "node": "24.9.0", "restrictedSession": false,
             "floor": "3.1.0", "signed": true },   // floor and signed from agent 3.1.0 (section 13)
  "config": { "ok": true, "source": "file", "problems": [] },
  "services": [ … ],
  "busy": { …aggregate… },
  "bootTargets": [ { "id": "windows", "name": "Windows 11" } ],
  "actions": [ { "id": "wake-legion", "name": "…", "confirm": null, "busyGated": false, "kind": "wol" } ],
  "autoUpdate": true,
  "updates": { …effective policy…, "inWindowNow": false, "nextWindow": "…", "lastCycle": {…} },
  "operations": { "running": [ opSummary ], "queued": [ … ], "recent": [ … ] },
  "controller": { "hash": "…", "id": "…", "revision": 12, "updatedAt": "…", "source": "mac" },
  "notes": [ … ],
  "t3": {…}, "pendingRestart": false, "lastUpdate": {…}, "connect": {…}   // 2.x
}
```

`config.source` is `file | defaults | last-known-good`. `config.ok: false`
blocks every mutation with `config-invalid`; reads keep working.

A client sends `--budget-ms` per attempt as
[section 15.5](#155-walking-attempts) says, and never sends a value below 1000.
The agent clamps it to 120000 and reads a missing or `0` value as 20000.

`operations.recent` holds **at most** five finished summaries, not exactly five.

Reachability is five separate things and they are never collapsed: the machine
is reachable (the ssh session), the agent answers (the reply), the service
process is up (`process`), the service answers (`health`), and the service is
reachable from outside (`endpoint`). `status` always reports
`endpoint.reachable: null`; only `doctor --deep` probes it.

`process.running` is evidence only when `process.error` is null; a client shows
the process as unknown otherwise.

`status.controller` deliberately does **not** carry the lineage. Status is
polled and lineage is up to 32 hashes; a client that needs it calls
`config meta`, and only when the hashes differ.

### Configured telemetry

`metrics` is optional, with at most eight entries:

```json
{"id":"queue-depth","name":"Queue depth","value":0,"unit":"jobs","checkedAt":"2026-09-05T14:01:00.000Z","error":null}
```

Each entry always carries `id`, `name`, `value`, `unit`, `checkedAt`, and `error`.
`value` is a finite number or null; a measured zero remains zero. A failed probe
has a null value and an error. A probe skipped because the shared status deadline
was spent also has `checkedAt: null`; attempted probes carry their check time.

Only `config.json`'s explicit `telemetry.probes` run. Absent/null telemetry or an
empty probe list omits `metrics` and collects nothing. Each probe defines a unique
configured id of at most 64 characters, a required command argv, optional `name`
(default id, at most 120 characters), optional `unit` (default empty, at most 24),
and `timeoutSeconds` (default 1, greater than 0 and at most 2). At most two probes
run concurrently, inside the shared status deadline. Stdout must contain one
finite decimal or exponent-form number. Unknown telemetry/probe fields are
configuration errors. See `schemas/telemetry.schema.json`.

### Administrative service configuration

This API edits machine-local `config.json`, separately from shared `controller.json`.
All three verbs require an unrestricted administrative session. `get` returns
`{hash,document,templates,limits:{maxBytes:1048576}}` with the standard envelope.
`hash` is always a lowercase SHA-256-shaped opaque structural identity. Reuse it
exactly; do not compute it using shared setup canonicalization. When no file
exists, `get` offers an inert seed document but the hash still identifies the
actual empty stored state.

`get` may also return `profiles`, an array of
`{id,name,platform,detected,availability,message,updateMethod,service}`. Platform is
`mac`, `windows`, or `linux`; availability is `available`, `not-installed`, `manual`,
or `unavailable`. `updateMethod` and the raw service draft may be null. Detection
does not imply that a supported unattended updater exists: a GUI-only update path
is reported as manual when it cannot run headlessly. Profiles describe supported
official methods and their limits, and service drafts keep automatic updates off
until the administrator explicitly enables them. Generic templates remain available
independently of this optional catalogue.

Both `validate --stdin` and `set --stdin` accept exactly
`{expectedHash:<get.hash>,document:<complete proposed config>}`. The document needs
`configVersion: 3` and an explicit `services` array. The one MiB input limit
includes this envelope; input has a five-second idle and fifteen-second total
deadline before the operation lock is taken.

Validation returns `valid: true`, the current `hash`, `proposedHash`,
`changes:{added,removed,changed,otherSettingsChanged}`, and `warnings:[{path,message}]`.
After an explicit save decision, `set` validates the exact proposed document again
under the operation/configuration locks and compares `expectedHash`. Success
returns `saved: true` and changes `hash` to `proposedHash`. A stale edit returns
`reasonCode: "stale-revision"`, `valid: false`, `conflict: true`, and the current
hash. Reload and review instead of retrying against a substituted hash.

Validation errors use `valid: false`, `reasonCode: "config-invalid"` or
`"bad-argument"`, and optional `errors:[{path,message}]`. Diagnostics omit command
argument values. Only `get` returns the document. Templates are incomplete drafts
for command, existing systemd user unit, and npm services; every saved service
requires an explicit busy probe or `busy.type: "none"`. Validation and saving do
not install packages, create units, or execute setup/service commands.

## 9. The shared setup and its lineage

### 9.1 Every device is a peer

There is no authority device, no authority flag and no follower mode. Every
client may edit and publish the setup, the phone included. This replaces the
earlier model in which one Mac was the only writer.

### 9.2 Why revisions are not enough

Revision numbers order documents that came from one writer. They cannot detect
divergence. Peer A at revision 5 edits to 6 and publishes to machines X and Y.
Peer B, offline from X and Y, edits its own revision 5 to 6 and publishes to Z.
A edits again to 7 and later reaches Z: 7 > 6, Z fast-forwards, and B's edit is
gone with nobody told.

What detects it is **ancestry**.

### 9.3 The controller block

Identity lives inside the document, under `controller`. `controller.id` is the
**setup** id — the fleet — shared by every peer and stable for the life of the
setup. It used to identify a device and no longer does.

```jsonc
"controller": {
  "id": "setup-3f9c2a71-…",
  "name": "Home setup",
  "revision": 12,
  "updatedAt": "…",            // display only, never compared: peers share no clock
  "source": "mac",             // mac | desktop | phone | cli | legacy
  "device": "Office MacBook Pro",
  "lineage": [ "<sha256 of the parent>", "<its parent>", … ]   // newest first, <= 32
}
```

Each lineage entry is the canonical hash ([section 12](#12-canonical-setup-bytes))
of an ancestor document.

### 9.4 What the agent accepts

`config set --controller-id ID --revision N [--replace]`, document on stdin.
The flags must match the document's `controller.id` and `controller.revision`,
or the answer is `bad-argument` and nothing is written.

With *held* = `{ id I, revision R, hash H, lineage LH }` and *pushed* =
`{ id i, revision r, hash h, lineage L }`:

| # | condition | answer |
| --- | --- | --- |
| 1 | nothing held, or held id is null (a 2.x copy) | store, `action: "stored"` |
| 2 | `i != I` | `--replace` → store, `action: "replaced"`, `replaced: true`; otherwise refuse `controller-conflict` |
| 3 | `h == H` | `action: "noop"`, nothing written |
| 4 | `H` is in `L` | fast-forward: store, `action: "stored"`. `r` must be `> R`, else `bad-argument` |
| 5 | `h` is in `LH` | refuse `stale-revision`: the pusher is behind |
| 6 | anything else | refuse `controller-conflict`, `divergent: true` |

**Revision order never decides acceptance.** Every refusal carries `current`,
the full held metadata including its lineage, so the client can choose between
fetching and merging without another round trip.

`--replace` applies to rules 2 and 6 only. It is an explicit human decision and
**no client ever sends it automatically.**

The document and its metadata are written in one crash-consistent transaction. A
reader never sees a revision that does not match the bytes beside it.

**Checks before writing.** `config set` checks, in this order, and the first
failure answers with nothing written: the size and UTF-8 rules of
[section 12](#12-canonical-setup-bytes) and that the canonical text parses as a
JSON object (`bad-argument`); that no object repeats a member name
(`config-invalid`), because implementations' parsers disagree about which copy
counts; the `controller` block and the flags; the table above; then, unless the
answer is `noop`, the document's structure (`config-invalid`): ids are tokens
and unique where [section 9.7](#97-document-acceptance) says, `machine.site` and
wake helpers name things that exist, helpers form no cycle and `wake.helper`
repeats `helpers[0]`, endpoint and `machine.ssh` hosts and users and every port
match `common.schema.json`, `systems[].shell`, `platform`, `restricted` and
`agent` have their documented types, and `appUpdates.githubRepo` is
`owner/name`. A `config-invalid` refusal carries `problems: [{path, message}]`
(at most 50). Warnings are accepted and returned in `notes`. A `noop` never
re-checks. Unknown keys are never a problem. Agents before 3.1.0 accept any
document that parses, so clients check before publishing as well.

**Restricted sessions.** When the session is restricted
(`status.agent.restrictedSession: true`), and the machine holds a copy, a push
the table would store or replace, `--replace` included, is refused with
`restricted` when [section 9.9](#99-launch-values-and-local-approval) would not
accept one of its launch values with the held document's launch values as the
approved ones, or when the held copy cannot be read. A restricted key can
therefore rename, route, add, remove, reorder, and reuse launch values the
machine already holds, but cannot introduce one. The refusal carries `current`,
and `launchChanges` — the paths of the refused values in document order, at most
100, never the values — when the held copy could be read. With nothing held the
ordinary rules apply. Unrestricted sessions are never refused for launch values;
this is defence in depth, and the client rule of section 9.9 is the boundary.

### 9.5 What clients do

State per device: the applied document `D`, its hash `Hd`, its setup id `Id`
and its lineage `Ld`. Keep the last 30 applied documents by hash, so a merge has
a base to work from.

Per machine `M`, in memory only:

- `meta`: `config meta` answers and the `current` of push refusals, filed under
  the hash they describe. A hash fixes the document, and with it the setup id
  and the lineage, so an entry never goes stale.
- `inFlight`, `failedAt[Hd]`, `held[Hd]`, `lockedAt` and `settled`: the
  guardrails below.

**Deciding.** On each successful `status` of `M`, let `S` be
`status.controller` and `X` be `meta[S.hash]` when there is one, else `S`. The
first row that matches decides:

| # | condition | decision |
| --- | --- | --- |
| 1 | `contract` absent or below 3, or no `status.controller` | `unsupported`: left out, never a conflict |
| 2 | this device has no applied document, or only an unrevisioned hand edit | `unknown` |
| 3 | `D` has no `controller.id` | `unknown`: it gets an identity first (below) |
| 4 | `S.hash` is null | `push`: M holds nothing |
| 5 | `S.hash == Hd` | `inSync` |
| 6 | `X.id` is null | `push`: M holds a copy nobody claims |
| 7 | `X.id != Id` | `differentSetup`: ask, with a change preview. Replace M's copy, or adopt M's setup here |
| 8 | `S.hash` is in `Ld` | `push`: M is behind |
| 9 | there is no `meta[S.hash]` | `readMeta`: call `config meta` once, then decide again |
| 10 | `Hd` is in `meta[S.hash].lineage` | `fetch`, expecting `S.hash` |
| 11 | otherwise | `diverged`: stop at a person |

A `config meta` answer whose `hash` is not `S.hash` means M changed in between:
file it, and decide on the next status. A push refused with `stale-revision` or
`controller-conflict` carries `current`: file it under `current.hash` and decide
again at once with `S = current`. A `current` without a hash is a failed request
(the guardrails), and only a reply with `ok: false` is a refusal.

**Automatic writes happen only along strict descent**: push when M's hash is my
ancestor, fetch when my hash is M's ancestor. Descent is acyclic, so two devices
can never take turns overwriting each other. Everything else stops at a person,
and the agent refuses any push that does not descend from what it holds.

**Admitting a fetch.** Read `config` and take `raw`, the stored document text. A
reply without `hash` is never adopted: none of the rows below is read, and it
counts as a failed request (the guardrails). An agent before 3.1.0 sends no
`raw`: the client may reconstruct `JSON.stringify(controller, null, 2)` in
received key order, and the hash check below decides whether that worked. With
`h` the canonical hash ([section 12](#12-canonical-setup-bytes)) of those
bytes, the first row that matches decides:

| # | condition | outcome |
| --- | --- | --- |
| a | the applied hash is no longer `Hd` | `headMoved`: nothing is written; decide again |
| b | `h` is not the expected hash, and it is the reply's `hash` | `moved`: M changed since the decision; decide on the next status |
| c | `h` is not the expected hash | `unverifiable`: never adopted; say that M's agent must be updated before its setup can be adopted automatically |
| d | the bytes fail [section 9.7](#97-document-acceptance) under peer intake | `invalid` |
| e | the bytes' own `controller.id` is not `Id`, or their own `controller.lineage` does not contain `Hd` | `inconsistent` |
| f | otherwise | `adopt` |

**Adopting is a compare-and-swap.** The bytes are stored exactly as fetched
(canonicalised, never re-serialised), so afterwards `Hd` is the hash that was
fetched. They replace the applied document only if the applied hash, re-read
from storage at the moment of writing, is still the `Hd` the decision was made
from. Otherwise nothing is written and the next status decides from the new
head. The same holds for Take theirs, Keep mine and Merge, whose expected head
is the document the divergence screen was built from.

Applying a document and running it are separate. After an adoption commits —
rule 10, Take theirs, Merge, Keep mine, or adopting a different setup at rule 7
— the client evaluates the new document's launch values against this device's
approvals ([section 9.9](#99-launch-values-and-local-approval)). No adoption
approves anything.

**Guardrails**, per machine:

- At most one setup request (`config meta`, `config`, `config set`) in flight,
  and at most one automatic push per `(M, Hd)` until its reply is read.
- After a failed request (no answer, an ambiguous answer, or a refusal not named
  below), nothing automatic goes to M for the same `Hd` for at least 60 s. A new
  `Hd` starts afresh.
- Never push during a running mutation on M: this device has an action in flight
  on M, or the latest status lists anything in `operations.running`. A push
  refused with `operation-in-progress` or `lock-held` is not a failure; it is
  tried again once a status read after the refusal lists nothing running. Reads
  are never held.
- `stale-revision` and `controller-conflict` refusals are information, not
  failures (above).
- A push refused with `restricted` or `config-invalid` is held for that
  `(M, Hd)`: it is not sent to M again automatically. The client says why — that
  M takes this revision only from a device whose key is not restricted (an
  unrestricted peer publishes it by rule 8 on its next poll), or the first of
  `problems` — and resumes when `Hd` changes or a person asks. Neither is
  divergence or a fault to back off from.
- A device whose applied document has a [section 9.7](#97-document-acceptance)
  error pushes nothing until it is fixed; it still reads and fetches, and merges
  as far as [section 9.8](#98-merging) allows.
- Nothing is remembered as "handled". The decision is recomputed on every status
  from `Hd`, `S.hash` and `meta`. Only the admission outcomes `invalid`,
  `unverifiable` and `inconsistent` are remembered, per (`Hd`, `S.hash`,
  `agentVersion`), and the document is not read again until one of the three
  changes.

**Editing**: the new document takes `revision: D.revision + 1` and
`lineage: [Hd, ...Ld]` truncated to 32. It becomes the applied document at once —
offline edits are first class — and publishing is the rule above on the next
poll. Several offline edits chain normally.

**A document with no `controller` block, or a block with no `id`**
(hand-written, or pasted from the example) gets a fresh setup id, revision 1 and
an empty lineage, keeping the block's other keys, before it is applied or
published, and the assigned id is shown once. Until then rule 3 keeps it out of
reconciliation.

**Divergence** must show both revisions, who wrote each (`source`, `device`,
`updatedAt`) and the entries of [section 9.8](#98-merging) that differ. It
offers Merge (default), Keep mine, Take theirs. Merge follows
[section 9.8](#98-merging). Keep mine is Merge with every entry answered mine: a
new revision whose lineage contains `Hm`, never `--replace`. Take theirs adopts
M's verified bytes unchanged.

Lineage is capped at 32. Two branches more than 32 revisions apart are reported
as divergence even when one is merely behind. **That fails toward a question,
never toward a loss.**

A 2.x agent cannot carry the setup and is excluded from reconciliation
entirely. It is never shown as a conflict.

Reference implementation: `contract/tools/setup-sync.mjs`. Vectors:
`contract/vectors/setup-reconcile.json`.

### 9.6 Unknown keys

Unknown keys are allowed anywhere in the document and **must be preserved when a
client edits it**. Edit the parsed JSON, not the typed model. A client that
round-trips through its model drops the keys it does not know, and because the
hash covers the whole document that deletion then looks like a deliberate edit
and propagates to every peer. Structural preservation is required; byte-for-byte
formatting is not.

A merge ([section 9.8](#98-merging)) preserves unknown keys too. An unknown
top-level key, and an unknown key of the `controller` block, is a merge entry of
its own: it is taken from the side that changed it and asked about when both
did. An unknown key anywhere else travels with the site, machine, endpoint,
system or wake block that contains it. Key order and number spelling are not
part of a document's meaning, and two values that differ only in them are equal.
A client nevertheless keeps both as it found them wherever it does not edit:
`22.0` stays `22.0`.

Schema: `contract/schemas/controller-document.schema.json`.

### 9.7 Document acceptance

Every client accepts exactly the documents `node contract/validate.mjs` accepts:
no more, no fewer. A document is refused when it breaks
`schemas/controller-document.schema.json`, or one of these rules:

| code | rule |
| --- | --- |
| `duplicate-member` | an object repeats a member name. Checked first, on the text; when it applies no other rule is reported |
| `schema` | any schema constraint: types, `version: 1`, required keys, `maxItems`/`minItems`, the token grammar for machine, site, endpoint and system ids, the configured-id grammar `^[A-Za-z0-9][A-Za-z0-9._-]*$` for `wake.helper(s).action`, the setup-id grammar `^[A-Za-z0-9][A-Za-z0-9._:-]{0,63}$` for `controller.id`, the lineage rules, the `source` enum, and the host, user, argv-item and repository guards of `common.schema.json` |
| `duplicate-machine` | two machines share an id |
| `duplicate-site` | two sites share an id |
| `duplicate-system` | two systems of one machine share an id |
| `duplicate-endpoint` | two endpoints of one machine share an id. Endpoints without an id are never duplicates |
| `unknown-site` | `machine.site` names no entry of a non-empty `sites` |
| `helper-self` | a machine is its own wake helper |
| `helper-unknown` | a wake helper names no machine |
| `helper-alias` | `wake.helper` differs from a non-empty `wake.helpers[0]` in `machine` or `action` |
| `helper-cycle` | the wake helpers form a cycle |

Nothing else refuses a document. What a client cannot use, it accepts and marks
as unusable, saying why:

| code | when |
| --- | --- |
| `no-machines` | `machines` is empty |
| `machine-no-systems` | a machine has no systems |
| `machine-no-endpoints` | a machine has no endpoints and no deprecated `ssh.host` |
| `system-no-agent` | a system's `agent` is absent or empty: it is not driven |
| `endpoint-no-id` | an endpoint has no `id`: it cannot be remembered as a route, and it merges with the other id-less endpoints |
| `endpoint-no-user` | an endpoint has no `user` |
| `endpoint-unknown-system` | an endpoint's `system` hint names no system of its machine; the hint is ignored |
| `endpoint-undialable` | an endpoint's or the deprecated `machine.ssh` host, user or port passes the schema but not [section 15.6](#156-addresses); it is never dialled |
| `wake-no-mac` | a wake block has no `mac`; direct wake is impossible, helpers still work |
| `wake-unplaced` | a wake block with no helper, no site and no `lanPrefix` |
| `wake-broadcast-defaulted` | a machine that can be woken directly (site or `lanPrefix`) has no valid broadcast at either level; direct wake uses the derived or limited broadcast (section 10.2) |
| `helper-alias-unused` | `wake.helper` beside an empty `wake.helpers`. 1.2 clients and every 1.4 client use it as the one helper (section 10.2), but not every 1.3 client does |
| `helper-other-site` | a helper at another site than its target |
| `helper-not-always-on` | a helper not marked `alwaysOn` |
| `shared-prefix` | two sites' valid prefixes overlap (section 10.1) |
| `prefix-invalid` | a `lanPrefixes` entry or `wake.lanPrefix` is not a prefix (section 10.1); it never matches |
| `prefix-without-dot` | a dotted prefix without the trailing dot; clients before section 10.1 also match `192.168.10.x` for `192.168.1` |
| `broadcast-invalid` | a `broadcast` entry is not a dotted IPv4 address; it is skipped |

**Intake.** *Peer intake* — documents read from a machine, kept revisions and
merge results — is checked as it is. *Local intake* — a document typed, pasted
or opened from a file — first gets an identity when it has no `controller` block
or no `controller.id` ([section 9.5](#95-what-clients-do)), and is then checked
the same way. *Applied intake* — the document this client already applies, read
at start or after an external write — is never refused as long as
[section 12](#12-canonical-setup-bytes) does not reject its bytes: its errors
are shown, the editor opens, publishing is held
([section 9.5](#95-what-clients-do)), and an error whose path is inside
`machines[i]` disables that machine (not dialled, not run); the document is
still used for deciding and divergence, and for merges as far as
[section 9.8](#98-merging) allows.

Section 12 comes first under every intake: a text it refuses is no document, so
it is reported as `schema` and not even applied intake keeps it. A
`controller.id` of null is no id. A wake helper is every entry of
`wake.helpers` and the alias `wake.helper`, so the alias is held to
`helper-self`, `helper-unknown` and `helper-cycle` as well, beside an empty
`wake.helpers` too. A `wake.lanPrefix` that is not a prefix places nothing, and
only a wake block with a `mac` is woken directly. Warnings are reported only
for a document without errors.

Reference: `contract/tools/document-rules.mjs`. Vectors:
`contract/vectors/setup-acceptance.json`.

### 9.8 Merging

A merge compares `mine` (`D`), `theirs` (M's verified document) and, when there
is one, `base`. The base is the first hash in `Ld`, newest first, that is also
in theirs' lineage, whose kept bytes still hash to it and which peer intake
accepts. A kept revision that peer intake refuses, kept by an older build, is
skipped exactly like one that is not kept. If there is no such hash there is no
base, and every difference is asked about.

Each side is held to the intake [section 9.7](#97-document-acceptance) gives
it. Theirs and the base pass peer intake. Mine is the applied document, which
applied intake keeps with its errors, so a device whose document breaks
`unknown-site`, `helper-self`, `helper-unknown`, `helper-alias` or
`helper-cycle` still merges: the result is checked like any other (below), and
taking theirs' side of the entry at fault repairs it. Any other error of mine
(`duplicate-member`, `schema` or a `duplicate-` rule) leaves its entries
undefined, so Merge and Keep mine wait until it is fixed in the editor; Take
theirs does not.

**Entries.** Each entry has a key and a value; "absent" is a value.

| key | value |
| --- | --- |
| `K` | each top-level key other than `controller`, `machines`, `sites`; written `"K"`, inside double quotes with nothing escaped, when `K` begins with `"`, `controller.`, `sites[` or `machines[`, so it never reads as another entry's key |
| `controller.K` | each `controller` key other than `id`, `revision`, `updatedAt`, `source`, `device`, `lineage` |
| `sites[ID]` | the whole site |
| `machines[ID]` | the whole machine, when mine or theirs lacks it |
| `machines[ID].fields` | the machine without `endpoints`, `systems`, `wake`, when both have it |
| `machines[ID].wake` | the wake block, when both have the machine |
| `machines[ID].systems[ID]` | one system, when both have the machine |
| `machines[ID].endpoints[ID]` | one endpoint with an id, when both have the machine |
| `machines[ID].endpoints[]` | the endpoints without an id, in order, as one value (none is absent) |

Two values are equal when they are the same JSON value: objects with the same
keys in any order and equal values, arrays element by element, strings by code
point, and numbers by exact decimal value (`22`, `22.0` and `2.2e1` are equal;
no floating point decides).

**Kinds.** For each entry where mine and theirs differ: `mine` — there is a base
and theirs equals it, take mine; `theirs` — there is a base and mine equals it,
take theirs; `both` — there is a base and both differ from it, including delete
versus edit; `noBase` — there is no base. `both` and `noBase` are preselected
theirs and always shown. Differences are listed in code-point order of their
keys.

**Building the result.** Start from mine. Remove every entry taken from theirs
that theirs lacks; if `endpoints[]` is taken from theirs, remove mine's id-less
endpoints. Replace every entry taken from theirs that mine has, in place. Then
walk each of theirs' arrays in order with a cursor: an element whose key is in
the result moves the cursor to it; an element taken from theirs that is not in
the result is inserted after the cursor (first when there is none) and becomes
the cursor. An endpoint without an id has no key of its own: when `endpoints[]`
is taken from theirs, each of theirs' id-less endpoints is inserted; otherwise
theirs' n-th id-less endpoint stands for the result's n-th, when there is one,
and only moves the cursor. Otherwise array order is mine's: a reorder alone is
not a difference. Object keys keep mine's order, with new keys appended. Values that
are not replaced keep their spelling, and number lexemes are never rewritten.

**Identity.** `id` is mine's. `revision` is one more than the higher of the two.
`lineage` is mine's hash, then theirs' hash, then the two lineages interleaved
(mine first), with duplicates dropped and the list cut at 32. `updatedAt`,
`source` and `device` are the writing device's. Unknown `controller` keys are
merged as entries.

The result is checked by [section 9.7](#97-document-acceptance) under peer
intake before it is applied. A merge that would be refused, for example a kept
helper that names a machine taken out, is not written, and the person is told
which rule it breaks.

Reference: `contract/tools/setup-sync.mjs`. Vectors:
`contract/vectors/setup-merge.json`.

### 9.9 Launch values and local approval

Lineage shows that a document claims an ancestor. It does not show who wrote it,
or that the writer may decide what another device runs: any key that may run
`config set`, a restricted one included, and anyone who can write
`controller.json` on a machine, can produce a valid descendant that changes
anything. So a client never takes **launch values** from replication alone. Each
device keeps its own record of the launch values it approved
([section 11](#11-private-bindings)) and runs only those. The document itself
still replicates and applies unchanged ([section 9.5](#95-what-clients-do)).

| launch value | path | why |
| --- | --- | --- |
| system tuple `{agent, grammar}` | `machines[<m>].systems[<s>]` | `agent` is the argv this device runs with its own key, and the command is appended to it, so arguments inside it are agent arguments: `["node", "<base>/bin/launcher.mjs", "self-update", "--rollback"]` passes a restricted dispatcher. `grammar` is [section 15.1](#151-which-grammar) applied to `platform`, `shell` and `restricted`: how the line is quoted. |
| `identityFile` | `machines[<m>].ssh.identityFile` | chooses a private key on this device (deprecated, section 11) |
| `githubRepo` | `appUpdates.githubRepo` | where this device's own updates come from; signatures stop a forged build, not a frozen or redirected source |
| `local` | `local` | the Mac runs `node <local.agent>` on itself (deprecated, section 11) |

Everything else replicates and applies automatically after sections 9.7 and
15.6: names, labels, `symbol`, `sites`, `machine.site`, `alwaysOn`, `endpoints`
including `user`, the deprecated `machine.ssh` host, user and port, and `wake`
including helpers. A route decides where this device sends its own approved
command; the pinned host key decides whether it sends anything there. A route is
not an authorisation: a peer can point a machine at another machine whose key
you pinned.

**Reading them.** From the parsed document, never through a typed model.
Machines and systems are matched by `id`; the first occurrence of a repeated id
counts. `agent` is the array when it is non-empty and every item is a string,
else null; a null `agent` makes the tuple inert. Otherwise `grammar` is section
15.1 with `restrictedSession` false, written `refused:<code>` when that section
refuses. `identityFile` is the non-empty string, else absent. `githubRepo`
absent, empty and `"x1f4r/legion-control"` all mean the built-in repository.
`local` is absent unless it is an object whose `enabled` is not `false`; then it
is `{ "agent": <the string, or null for the default path> }`. Values compare as
JSON: arrays in order, strings by code point, no case folding, no path or
Unicode normalisation.

**Accepted without asking.** A value this device approved at any place in the
setup may be used at any place in it. Also accepted:

1. an inert tuple, which means nothing runs on that system;
2. no `identityFile`, the built-in repository, no `local`, or a `local` whose
   `agent` is null;
3. the launcher migration of an approved tuple: the same grammar, equal except
   one `agent` item, which was `<base>/agent/src/index.mjs` and is
   `<base>/bin/launcher.mjs` with the same non-empty `<base>` containing no `..`
   segment, compared after replacing `\` with `/`. The reverse is not accepted.

**Everything else waits.** The document is applied all the same, so hash and
lineage advance and replication continues. On this device:

- a system runs with the tuple last approved at that machine and system; with
  none it is not driven and no command line is built for it;
- an unapproved `identityFile` gives way to the one last approved for that
  machine, or none; an unapproved repository to the approved or the built-in
  one; an unapproved `local` to the approved one, or none;
- a person is shown each waiting value beside the approved one, with the
  revision's `controller.device` and `source` marked as unverified. They may
  **Approve** (record exactly the values shown), **Revert** (an ordinary edit
  restoring the approved value, which replicates), or leave it. A value that
  cannot run — an argv item, `identityFile` or `local.agent` holding a control,
  invisible or bidirectional formatting character, an item over 4096 UTF-8
  bytes, a refused grammar, or a repository that is not `owner/name` — can only
  be reverted or left.

A value that cannot run itself, by the rules of the last item, is never used:
an accepted one falls back as the first two items say, and a recorded one counts
as none there.

**What approves, and nothing else does:** a decision above; an edit made on this
device — an editor, a paste, a hand edit of the setup file that keeps its
`controller` block — for the values it changed; a setup file with no
`controller` block, or none with an `id`, that a person put on a device applying
no setup yet, which is that device's first setup and approves every launch value
it holds, as the same text pasted would (put over an applied setup, such a file
is a setup of its own and approves nothing, so what it changed waits); enrolment, importing a setup
into a device that applies none, in the explicit import or fetch flow, after
showing all of its launch values; and, once, the first start of a client
implementing this section, which records the launch values of the document it
already applies. Automatic fetch, Take theirs, Merge, Keep mine, adopting a
different setup and restoring a kept revision approve nothing.

Reference: `contract/tools/launch.mjs`. Vectors: `contract/vectors/launch.json`
([section 14.2](#142-vectors)).

## 10. Sites, wake and routing

### 10.1 Sites

`sites[]` says where the LANs are; `machine.site` places a machine on one.

**A LAN prefix is a hint and never proof.** Two sites may have identical private
subnets, because home routers ship the same default range, and matching
`192.168.50.` says nothing about which of two homes a device is in. A client
that matches more than one site treats its location as **unconfirmed** and never
picks the first. The private binding `currentSite` is the user's own answer to
that ambiguity, and it is a routing hint too: it never authenticates anything.

What authenticates a machine is its **pinned ssh host key**, never its address.
A known remote address is never rejected because a local prefix happens to
resemble another site.

#### Prefixes

A `sites[].lanPrefixes` entry, and the deprecated `wake.lanPrefix`, is one of:

- **dotted**: one to three decimal octets, optionally followed by a single dot:
  `10`, `10.`, `192.168.1`, `192.168.1.`. It matches an IPv4 address whose
  leading octets are exactly those. `192.168.1` matches `192.168.1.7` and never
  `192.168.10.7`.
- **CIDR**: a dotted-quad network, `/`, and a length from 8 to 32, with no host
  bits set: `192.168.16.0/20`. It matches every IPv4 address inside it.

Octets are `0`–`255` without leading zeros. Anything else (a full address
without a length, host bits set, IPv6, wildcards, surrounding whitespace) is not
a prefix: it never matches, editors refuse it, receivers warn (`prefix-invalid`,
section 9.7), and a document is never refused for it. Editors write an
octet-aligned prefix in dotted form with the trailing dot, because a client that
predates this section compares text with "starts with" and is right only when
the prefix ends in a dot. Such a client never matches a CIDR prefix and so treats
itself as off-site, the safe direction.

#### Placement

The candidate addresses are this device's IPv4 addresses on interfaces that are
up and can carry a broadcast: never loopback, never a tunnel or point-to-point
link, and on Android never a network with `TRANSPORT_VPN` or one the system
reports blocked for the app.

- **matching**: every site, in document order, with a valid prefix that matches
  a candidate.
- If the binding `currentSite` names a site S in `sites[]`, S is **effective**
  when S has no valid prefix or one of its prefixes matches a candidate;
  otherwise nothing is effective. A `currentSite` that names no site is ignored.
- Otherwise exactly one matching site is effective. None or several means
  nothing is; several is **ambiguous** ("site unconfirmed").

Machine M is **on this device's network** when M names a site in `sites[]` and
that site is effective, or, only when M names no such site, when M's valid
`wake.lanPrefix` matches a candidate. The first candidate that matched is the
**placing address**. Route order ([section 10.3](#103-routes)) and direct wake
both use this one test. Clients recompute placement from the current interfaces
at least on every poll and immediately before planning a wake.

Reference implementation: `contract/tools/wake-plan.mjs`. Vectors:
`contract/vectors/wake.json`.

### 10.2 Wake

Wake uses a configured action on a helper machine. There is no wake verb on the
wire: the client runs `run <action>` on the helper.

An agent action is either a `command` (the configured argv) or a `wol`, which
the agent sends itself:

```jsonc
{ "id": "wake-legion", "name": "Wake Legion",
  "wol": { "mac": "AA:BB:CC:DD:EE:FF", "broadcast": ["192.168.50.255"], "ports": [9, 7], "repeats": 3 } }
```

`repeats` defaults to 3 and is capped at 10. The agent sends that many standard
102-byte magic packets to every broadcast and port from an unbound UDP socket
with `SO_BROADCAST`, and reports `sent N packets to …`. Zero packets sent is
`failed` with `internal` and a message naming the address that refused. `wol`
actions are not busy-gated by default and take the operation lock like any
other. `status.actions[].kind` distinguishes them.

#### The plan

Waking target T is an ordered list of steps.

1. **Direct**, when T's wake block has a `mac` and T is on this device's network
   ([section 10.1](#101-sites)):
   - broadcast: the dotted-IPv4 entries of `wake.broadcast`; if none, those of
     T's site's `broadcast`; if none, the directed broadcast of the placing
     address (all host bits set) when its prefix length is known and at most 30;
     otherwise `255.255.255.255`. Other entries are skipped and never resolved
     as names.
   - ports: the entries of `wake.ports` from 1 to 65535; if none, `[9, 7]`.
   - three standard 102-byte magic packets to every broadcast and port, from a
     socket with `SO_BROADCAST`; on Android, bound to the network holding the
     placing address.

   Otherwise the direct step is skipped as `no-mac` (T has no `wake.mac`),
   `ambiguous` (T's site is among several matching sites), `unplaced` (T names
   no site in `sites[]` and has no valid `wake.lanPrefix`) or `elsewhere`.
2. **Helpers**: `wake.helpers` when non-empty, else `[wake.helper]`, else none,
   in that order. An entry is skipped, checked in this order, as `missing` (no
   such machine), `self` (T itself), `duplicate` (same machine and action as an
   earlier entry), or, from the helper's last status read and never from an
   extra one: `asleep` (that read failed with `noRoute` or `hostUnreachable`),
   `unusable` (it failed with `authenticationFailed`, `hostKeyChanged`,
   `hostKeyUnknown`, `interpreterMissing`, `agentMissing` or `badRequest`, or no
   system of the helper is approved on this device,
   [section 9.9](#99-launch-values-and-local-approval)), `no-action` (its status
   lists `actions` without this id) or `held` (a wake hold for T exists and its
   status does not declare this action `kind: "wol"`). A helper not read in this
   session, or whose last read ended any other way, is read once just before its
   step; if it is still not ready it is skipped as `asleep` when that read failed
   with `noRoute` or `hostUnreachable`, and as `unusable` otherwise.
3. With no direct step and no helpers at all, the plan says so (`none`).

#### The walk

Steps run in order. A direct step from which no packet left, a helper skipped at
its step, a pre-dispatch failure and any terminal result other than `ran` move
straight to the next step. A direct step that sent packets, or a helper action
that finished `ran`, is followed by **readiness**: the client's ordinary
authenticated status poll of T, first after 5 s, then at intervals growing 1.6×
to at most 20 s, for 120 s from the send. T answering ends the wake. No answer
moves on to the next step. After the last step the client says T did not come
up, with one line per step taken and per entry skipped.

**Helpers are never woken automatically** and never cascade. A helper skipped as
`asleep` that has its own `wake` block is offered as "wake it first": a separate
press that runs that helper's own plan and nothing after it. No client polls a
helper more often than any other machine.

**Sending a packet is not waking a machine.** Only an authenticated answer from
T counts.

#### Wake holds

A `wol` action is a pure declared send and is idempotent. Any other action may
do anything, and an ambiguous result must not lead to it running on a second
helper.

A helper action ends **ambiguously** when the request may have been dispatched
and no terminal record has been read: a dropped link, a timeout, an unexplained
ssh failure after dispatch, or a reply still `queued` or `running` when the
client stops watching. If the helper's status does not declare that action
`kind: "wol"`, the client records a **wake hold** for T on that operation,
durably in its own operation history and never published. On a contract 3
helper it then reads `op <id> --wait 20` once. While any hold for T exists:

- no helper step for T runs unless its action is a declared `wol`, the held
  helper included. Direct steps and declared `wol` helpers still run;
- before planning a wake of T, the client reads `op <id>` once on each held
  helper that speaks contract 3 and was not last seen asleep.

A hold is released when the held record reads `state: "finished"` (whatever its
result), when the helper answers that it has no such operation (`op: null`, with
`not-configured` or, from 3.0.x, `bad-argument`), when T answers an
authenticated status after the hold was recorded, when the held helper leaves
the setup, or when a person explicitly takes one of the two ways past it below.
It is never released by time, by the client restarting, by a network change, or
by the held helper being unreachable. A 2.x helper keeps no records, so a hold
on one is released only by T answering, by the helper leaving the setup, or by a
person. Holds are per device.

Going past a hold is a person's explicit choice, made after the holds were read
as above, and it has exactly two forms. Every client offers the same one in the
same situation:

- **Try the other helpers** is offered when the plan as if nothing were held,
  without the helper steps the holds are on, asks a helper that the plan as it
  stands skips as `held`. It releases the holds for T and walks exactly that
  plan, so a held command is never run a second time by it; the next wake asks
  every helper. When it would ask nobody new, nothing is released and the
  client says that no other helper could be asked.
- **Run the held command again** is offered only when no other helper could be
  asked instead, and only after telling the person that the first run may still
  be going and that this can run it a second time beside it. It releases the
  holds for T and walks the plan as if nothing were held.

No other choice, and nothing a client does on its own, runs a held command
again while its hold could stand.

Boot and sleep are never retried without reconciling the operation first.

`wake.helper` (singular) is the compatibility alias for `helpers[0]`. An editor
writing `helpers` must also write `helper`, so a 1.2 client keeps the one helper
it understands. **A 1.2 client does not do failover and must not be described as
if it did**: it loads the additive fields and keeps its old behaviour. Contract 3
clients are required for the peer features.

### 10.3 Routes

Endpoints keep their `system` hint. After a boot to system X, or an observed
system change, the client forgets the remembered route for that machine and
dials endpoints hinted `X` first, then `lan` when on site, then the rest,
honouring the per-address backoff of at least 60 s. A status reporting a
different `system.id` is still accepted — the hint is routing only — and the
route is re-remembered.

No bare TCP probe before a normal authenticated call on a remembered route.

## 11. Private bindings

What one device knows about itself and never publishes: which machine it *is*,
where its keys are, which ssh aliases exist in its own config, and how to run an
agent on itself without ssh.

Schema: `contract/schemas/bindings.schema.json`. Stored beside the setup file
(Android: DataStore), relocated with the rest of the local state when
`LEGION_CONTROL_HOME` is set, so an isolated test run cannot touch the real
`~/.ssh`.

None of it is publishable. An `identityFile` is an absolute path that means
nothing on another device, and a shared document carrying one makes every peer's
copy differ for a reason none of them chose. The shared
`machine.ssh.identityFile` and top-level `local` are deprecated launch values
([section 9.9](#99-launch-values-and-local-approval)), used only at values this
device approved, and never stripped automatically — removing them would change
the bytes, and so the hash, on whichever device opened the document first.

A binding names **where** a key is, never what it is. No private key is ever
copied, published or merged.

Effective ssh identity for a machine: the per-machine binding, else the device
default, else the deprecated shared value when this device approved it, else the
client's own default key. **Explicit endpoints inherit it** — dropping the
identity on an endpoint the user spelled out is how a working machine becomes
unreachable for no visible reason.

`self` marks the machine this device is. With `localAgent`, every command is run
by spawning `localAgent.argv + command` directly: no ssh, and no shell field,
because wrapping the argv in `cmd` or `powershell` would add a quoting layer with
no ssh anywhere on the path to need one. Without `localAgent` the machine is
driven over ssh like any other, and the client never invents a loopback endpoint.

Boot and sleep on `self` are allowed, with the normal confirmation plus a note
that this device is the controller and the outcome is read from the operation
record after it comes back. The record is the evidence; uptime is not.

Android never sets `self` or `localAgent` — the phone cannot run a service, which
the app says outright rather than showing an empty section — and has exactly the
same right to edit and publish as every other device.

Approved launch values (section 9.9) are private in the same way, but kept in
their own record so that an older build rewriting the bindings cannot drop them:
`approved-launch.json` beside the applied-setup state (Android: the
`approved-launch` preference beside the setup text). Its shape, informatively:
`{ "schema": 1, "seededFrom": <hash or "none">, "machines": { <machine id>: { "systems": { <system id>: { "agent": [..], "grammar": ".." } }, "identityFile": ".." } }, "githubRepo": "..", "local": { "agent": .. } }`.
Deleting it makes the next start record the applied document again.

## 12. Canonical setup bytes

One document, one hash, on all four sides.

1. Decode as UTF-8. **Refuse** anything that is not valid UTF-8; it has no hash.
2. Strip one leading `U+FEFF`, and only if it is the very first code point.
3. Replace every CRLF with LF, then every remaining lone CR with LF.
4. Strip `U+0009 U+000A U+000B U+000C U+000D U+0020` from both ends, **and
   nothing else**. Do not use the language's own trim: JavaScript's `String.trim`
   also strips `U+00A0` and `U+FEFF`, Java's `String.strip` follows
   `Character.isWhitespace`, and .NET's `Trim` uses a third table. A document
   beginning with a non-breaking space must hash the same everywhere.
5. Append exactly one LF.
6. The hash is the lowercase hex sha256 of those UTF-8 bytes, and those bytes
   are what is stored on disk.

The agent returns those stored bytes as `raw` from `config`.

Reference implementation: `contract/tools/canonical.mjs`. Test data:
`contract/hash-vectors.json`, which every client and the agent must reproduce
vector by vector — including the ones with no hash, which must be refused.

Before anything is stored or sent, a document is refused — by the agent on
`config set`, and by a client before it publishes, pastes, imports or adopts it
— for the first of these that applies: `too-large` (more than 1048576 bytes as
given), `invalid-utf8`, `empty` (the canonical bytes are a single LF),
`not-a-json-object` (the canonical text does not parse as a JSON object with a
numeric `version` and an array `machines`). The `empty` and
`not-a-json-object` decisions are made on the canonical bytes, never on the
bytes as given, so a byte order mark or surrounding whitespace never makes a
document unparseable. The hash vectors' `accepted` and `reject` are this rule.

## 13. Trust and the restricted session

The release trust key is `contract/release-public-key.pem`, an Ed25519 SPKI PEM.
Clients and the agent embed its actual value. A downloaded key is never trusted.

`self-update` verifies the manifest signature and every file hash against the
key the running agent was built with, **before** the archive is extracted. It
then stages, runs the staged tree's own `version --check`, and only then swaps,
keeping the previous tree. The self-test must report its internal checks passed
and the exact signed version and contract. `--rollback` verifies the complete
previous tree before executing a prepared copy; unsigned legacy backups remain
retained for manual recovery and never gain a publisher-verification claim.

The reply's `manifest` is the internal `agent/MANIFEST.json` summary
(`{ schema, version, contract, files, signatureVerified }`, plus an optional
`keyFingerprint`), not the release-artifact manifest.

`self-update --stdin` reads the tarball from stdin and is the upload path for a
restricted session, which has no shell and therefore no `cat >`. It does **not**
combine with `--install`.

Upload reads have a 64 MiB cap, fifteen-second idle deadline and two-minute total
deadline, and complete before taking the operation lock. Installs bind their
operation id to the exact archive hash; bootstrap binds it to the internal
manifest hash. Rollback binds a distinct target and retries replay that original
target even after the previous-tree path changes.

For a recognized install base, a 2.x bootstrap runs the locally verified new tree
at `<base>/incoming/agent/src/index.mjs self-update --install --op ID`. It derives
the base from that path, rejects a conflicting `LEGIONCTL_HOME`, and does not use
the current working directory. The signed recovery helpers are atomically
published to `<base>/bin` before the first live rename. A journal and an anchored
local inventory identify the old live tree for crash recovery. This local
inventory is not a release signature and authorizes only restoration of that
pre-swap state after interruption, not ordinary unsigned rollback. Recovery
restores old live in a missing-tree gap without running an unverified candidate;
post-commit backup cleanup failures keep the successful outcome and report the
actual retained path in notes.

New generated endpoints use the stable launcher. An existing explicit agent argv
is preserved; migration to the launcher is a separate reviewed setup edit that
retains the interpreter and install base. Other devices accept exactly that
migration without asking ([section 9.9](#99-launch-values-and-local-approval)).
An unrecognized custom path requires an explicit base/path choice rather than a
guessed upload destination. Existing direct entry paths cannot themselves
recover a missing live-tree gap.

A restricted session is a forced command that parses a limited quoted argv
grammar and never hands anything to a shell. It reports
`status.agent.restrictedSession: true`. Because the dispatcher is not a shell, a
client must serialise with the `dispatch` grammar of
[section 15.2](#152-serialising-an-argv) whatever the system's configured
`shell` says; a client knows a system is restricted from its approved tuple's
grammar being `dispatch` ([section 9.9](#99-launch-values-and-local-approval)),
or from a status over that route reporting `agent.restrictedSession: true`
([section 15.1](#151-which-grammar)).

A restricted key can publish the setup (`config set` on stdin), except a
document carrying a launch value the machine does not already hold, or over a
held copy the machine cannot read ([section 9.4](#94-what-the-agent-accepts)),
and can trigger a helper's wake action (`run <id>`). It cannot reach the agent's
own service configuration, `authorized_keys` or the trust key through the shared
document, and the document never carries public keys or anything an agent would
apply to `authorized_keys`. Whatever any key publishes, a client runs only
launch values it approved itself
([section 9.9](#99-launch-values-and-local-approval)). Key enrolment stays out
of band.

A reply to a restricted session is redacted before it is written. Every
configured command argument after the executable, every credential-named
configuration value and every credential inside a configured URL — taken from
the current `config.json` and from the last copy that loaded cleanly — is
replaced by `<redacted>` wherever it appears in free text: messages, errors,
reasons, notes, log lines, progress notes and command output. Identifiers, enum
values, versions, timestamps, hashes, paths in `problems` and `launchChanges`,
and the setup document (`controller`, `raw`, `meta`, `current`) are never
altered, so a redacted reply still validates. In every session a failed command
is named by its executable, never by its arguments, and a `config.json` that
does not parse is reported by line and column, never quoted. Redaction cannot
recognise a secret that appears only in a command's own output: treat a
restricted key as able to read what configured commands print.

### Version floor

Every signed agent declares the oldest agent it may be replaced by, in its
signed `package.json` as `legionControl.agentFloor` (at most its own version).
The agent keeps the highest floor it has committed at `<base>/agent-floor.json`,
outside the replaceable tree; the effective floor is the higher of that file and
the live tree's declaration, and is reported as `status.agent.floor` and as
`floor` on every `self-update` reply. Both are `null` when the agent can state
no floor: the file cannot be read, or there is no file and the live tree
declares none (a 2.x or 3.0.x tree).

- A restricted session may install only a bundle at or above both the live
  version and the floor, and may `--rollback` only to a retained tree at or
  above the floor. Anything else is `restricted`.
- An unrestricted session needs `--allow-downgrade` to install below the live
  version, or to install or roll back below the floor; without it the answer is
  `bad-argument` and nothing is staged. With it the floor is set to the target
  before the swap. The dispatcher refuses the flag.
- Refusals happen before an operation record exists. Only a committed install
  raises the floor. Interrupted-swap recovery restores the pre-swap tree without
  consulting it.
- The stable launcher refuses to execute a signed live tree below the floor.
- A client sends `--allow-downgrade` only after an explicit decision, and only
  to an agent whose `status.agent` carries `floor`.

## 14. Fixtures and vectors

Everything in `fixtures/`, `vectors/` and `hash-vectors.json` is generated from
`contract/tools`. `node contract/tools/generate.mjs` writes it;
`node contract/tools/generate.mjs --check` writes nothing and fails when a
committed byte differs from what the generators produce, or a file in
`fixtures/` or `vectors/` is missing or extra. Edit the generators, never their
output.

### 14.1 Fixtures

`contract/fixtures/index.json` lists every fixture with the schema it validates
against. **Read the index and walk `fixtures`; do not glob the directory.** Each
entry carries:

| field | |
| --- | --- |
| `file` | the fixture in this directory |
| `kind` | `reply` or `document` |
| `expect` | `valid`, or `invalid` for fixtures that exist to be refused |
| `command`, `variant` | which answer to which command; `config meta` and `config set` are commands of their own |
| `schema` | the schema in `contract/schemas` it validates against |
| `ok`, `exitCode`, `contract`, `action`, `reasonCode`, `outcome` | for replies; `exitCode` is the one rule 7 gives |
| `tags` | so a client test can take a subset |

Naming is `<command>.<variant>.json`. Replies from a 2.x agent are prefixed
`legacy-2x.` and validate against a `legacy-2x-*.schema.json`.

A client's fixture test handles every entry, in order, and fails on one it has
no handler for:

- A `reply` is decoded with the decoder the client uses for its `schema`. Its
  `ok`, `action`, `reasonCode` and, when not null, `outcome` equal the entry's;
  every `reasonCode` in the file is one the client renders by code; for a
  status, the client's contract gate agrees with `contract`. The client's
  attempt classification ([section 15.4](#154-reading-an-attempt)) of
  `exitCode`, with the file as stdout, empty stderr and an empty ssh log, is a
  reply that decodes to the same values.
- A `document` goes through the client's own intake for its `schema` —
  [section 9.7](#97-document-acceptance) peer intake for the setup document, the
  bindings rules for `bindings.schema.json` — and is refused exactly when
  `expect` is `invalid`. A client that keeps none of a schema's keys in a file
  names that schema in its test, and still fails on any `invalid` fixture of it
  that it has not accounted for by name.

### 14.2 Vectors

A vector pins a function every implementation must compute identically.
`contract/vectors/index.json` lists the families, each with its file, its schema
(`schemas/<family>-vectors.schema.json`; the `hash` family keeps
`contract/hash-vectors.json`, `hash-vectors.schema.json` and its flat layout),
the section it pins and its zero-dependency reference implementation in
`contract/tools`:

| family | file | section |
| --- | --- | --- |
| `hash` | `hash-vectors.json` | 12 |
| `identifiers` | `vectors/identifiers.json` | 1, rule 5 |
| `outcome` | `vectors/outcome.json` | 5.6 |
| `transport` | `vectors/transport.json` | 15 |
| `setup-acceptance` | `vectors/setup-acceptance.json` | 9.7 |
| `setup-reconcile` | `vectors/setup-reconcile.json` | 9.5 |
| `setup-merge` | `vectors/setup-merge.json` | 9.8 |
| `launch` | `vectors/launch.json` | 9.9 |
| `wake` | `vectors/wake.json` | 10.1–10.2 |

The index's `section` holds section numbers only, so it lists the identifiers
family under `1` and the wake family under `10`.

A family file holds `groups`; each group is a list of cases
`{name, purpose, consumers, tags, input, expect}`. `name` is unique within the
family. `consumers` names who must run the case: `agent`, `mac`, `desktop`,
`android`. The index records, per group, how many cases each consumer runs. A
consumer's test reads the index first and fails if it, or any file it names, is
missing; has exactly one adapter per group that lists it and none for a group
that does not; feeds each case's `input` to the production function that group
pins and compares the result with `expect`; and fails unless it ran exactly the
number of cases the index gives it. A vector is never skipped.

Every key of `expect` is present, `null` where it does not apply, and numbers in
`expect` are integers. Objects compare by key set in any order, arrays element
by element, strings by code point, booleans and null by identity. A string field
whose name ends in `Text` is a JSON document, compared as parsed documents with
object key order ignored and number lexemes exact.

The hash vectors carry `inputBase64`, `canonicalBase64` and `sha256` — base64
because a JSON string cannot hold a lone CR or an invalid byte.

Every `expect` was produced by the reference implementation and also stated by
hand in the case tables (`contract/tools/vectors/*.cases.mjs`); generation
refuses a case whose two statements disagree. `node contract/validate.mjs` lints
the schemas, validates every fixture and vector, asserts the rules a schema
cannot express, runs every reference over every case, and repeats the checks it
has a separate implementation for. `node --test contract/test/*.test.mjs` runs
the same checks plus the validator's own tests and injected defects. Use the
glob: the directory form of `--test` does not work on Node 26.

If this prose and a fixture or vector disagree, the fixture or vector wins and
this file is a bug.

## 15. Command lines and retry safety

ssh runs a string, not an argv, and its exit status mixes its own failures with
the remote command's. Every client turns the same argv into the same bytes and
reads the same evidence the same way. Reference implementation:
`contract/tools/transport.mjs`. Vectors: `contract/vectors/transport.json`,
which every client reproduces case by case. Where this prose and a vector
disagree, the vector wins.

### 15.1 Which grammar

A system is **restricted on a route** when its `restricted` is the JSON value
`true`, or the last authenticated `status` over that route reported
`agent.restrictedSession: true`.

| restricted on the route | `shell` | `platform` | grammar |
| --- | --- | --- | --- |
| yes | any | any | `dispatch` |
| no | `posix`, `cmd` or `powershell` | any | that value |
| no | absent or null | `windows` | `cmd` |
| no | absent or null | anything else, or absent | `posix` |
| no | any other value | any | refused: `unknown-shell` |

`cmd` is the Windows default because it is what a stock Windows OpenSSH runs. A
client never infers PowerShell and never retries a command in another grammar. A
`dispatch` system's `agent` is exactly two elements, interpreter and entry; any
other length is refused as `restricted-agent-shape`. `unknown-shell` arises only
in a document kept under applied intake
([section 9.7](#97-document-acceptance)); such a system is not driven. The
launch tuple ([section 9.9](#99-launch-values-and-local-approval)) records the
grammar computed without `restrictedSession`; a route's status can only move a
system to `dispatch` at run time. Editors write `shell` for every Windows system
they create or change. On Windows, `legionctl doctor` reports which shell the
account's OpenSSH runs as check `ssh.shell`.

### 15.2 Serialising an argv

The argv is the system's effective `agent` (section 9.9) followed by the command
and its arguments. Elements are checked in order; the first that fails refuses
the whole line with the code given, and nothing is sent. An empty argv is
refused as `no-command`. Tokens are joined with exactly one U+0020.

Every grammar refuses an empty element (`empty-argument`) and an element
containing U+0000–U+001F or U+007F (`control-character`). A refusal carries the
index of the element that failed, counted from 0, or null when it refuses the
whole argv or line: `no-command`, `too-many-arguments` and `line-too-long`.

**posix** and **dispatch.** An element is written bare when it matches
`^[A-Za-z0-9._/:@+,-][A-Za-z0-9._/:@+,=-]*$` and, for the first element only,
contains no `=`. Otherwise it is `'`, the element with every `'` replaced by
`'\''`, and `'`. `~` is never bare: argv elements are literal and nothing
expands them. `posix` also refuses an element in which a backslash is followed
by another backslash, by `'`, or by the end of the element (`posix-backslash`),
because fish reads those as escapes inside single quotes. sh, dash, bash, zsh,
ksh and fish are supported; csh and tcsh are not. `dispatch` does not refuse
those, and instead enforces the dispatcher's limits: more than 64 elements
(`too-many-arguments`), an element over 4096 UTF-8 bytes (`argument-too-long`),
a line over 16384 UTF-8 bytes (`line-too-long`). The number of elements is
checked before any element, and the line only after all of them.

**cmd.** Refuses an element containing `"` (`double-quote`), `%` (`percent`) or
`!` (`exclamation`). Every element is written as `"`, the element, its trailing
run of backslashes once more, and `"`. A backslash anywhere else stands for
itself (the C runtime rule). The line is `@` followed by the tokens, so `cmd /c`
uses it verbatim whether or not sshd wrapped it in quotes. Inside the quotes
`& | < > ( ) ^` are literal.

**powershell.** Refuses an element containing `"` (`double-quote`), ending in
`\` (`trailing-backslash`), containing two consecutive U+0020
(`double-space`), or equal to `--%` (`stop-parsing`), which PowerShell reads
as its stop-parsing token even when it is quoted. Every element is written as `'`, the element with each of
U+0027, U+2018, U+2019, U+201A and U+201B written twice, and `'`. The line is
`& ` followed by the tokens.

### 15.3 What the dispatcher accepts

`dispatch` is the grammar `agent/src/dispatch.mjs` parses from
`SSH_ORIGINAL_COMMAND`: at most 16384 UTF-8 bytes; tokens separated by runs of
U+0020 or U+0009; outside quotes, `'` opens a run that ends at the next `'` and
is literal throughout; outside quotes `\'` is one literal `'` and any other
backslash is refused; outside quotes `` $ ` ; & | < > ( ) { } * ? ! # " `` LF,
CR and NUL are refused and every other character stands for itself; adjacent
runs concatenate and `''` is an empty token; at most 64 tokens of at most 4096
UTF-8 bytes. Token 1 must be the agent's interpreter (by realpath, or `node`),
token 2 its entry or stable launcher, token 3 a restricted command, and every
later token matches the generic grammar of rule 5 or is `--name` or
`--name=VALUE` with VALUE in that grammar. Section 15.2 never produces anything
outside this.

### 15.4 Reading an attempt

Evidence: whether ssh could be started; whether the client terminated it (its
watchdog or a cancellation); the exit status, absent when the channel closed
without one; stdout; stderr; and ssh's own log. An OpenSSH client runs ssh with
`-o LogLevel=ERROR -E <file>` and a fresh file per attempt, readable only by the
user. **Remote stderr is never evidence of where a command stopped.** Blank
means only U+0009, U+000A, U+000D and U+0020.

| # | evidence | kind | dispatch |
| --- | --- | --- | --- |
| 1 | ssh could not be started | `launchFailed` | `never` |
| 2 | stdout from its first `{` to its last `}` is a JSON object | reply | `acknowledged` |
| 3 | the client terminated the process | `timedOut` | `unknown` |
| 4 | no exit status | `linkLost` | `unknown` |
| 5 | exit 255, blank stdout, a log line matches the pre-dispatch table | that row's kind | `never` |
| 6 | any other exit 255 | `linkLost` | `unknown` |
| 7 | exit 126, 127 or 9009 with blank stdout | `interpreterMissing` | `never` |
| 8 | stderr contains `cannot find module` or `err_module_not_found` | `agentMissing` | `unknown` |
| 9 | stderr contains `is not recognized as`, `commandnotfoundexception` or `cannot find the path specified` | `interpreterMissing` | `unknown` |
| 10 | anything else | `unreadableOutput` | `unknown` |

Rows apply in order. Substring tests in 8 and 9 are ASCII case-insensitive. A
reply the client cannot decode is `unreadableOutput`, `acknowledged`. A line
refused by section 15.2 or 15.6 is `badRequest`, `never`. The route-level kinds
are `noRoute`, `launchFailed`, `hostUnreachable`, `connectionRefused`,
`authenticationFailed`, `hostKeyChanged`, `hostKeyUnknown`, `timedOut` and
`linkLost`.

Pre-dispatch table: each log line with one trailing CR removed, ASCII
case-insensitive; the first row with any matching line wins.

| kind | patterns |
| --- | --- |
| `hostKeyUnknown` | `^No [^ ]+ host key is known for .+ and you have requested strict checking\.$` |
| `hostKeyChanged` | `REMOTE HOST IDENTIFICATION HAS CHANGED`; `^Host key for .+ has changed and you have requested strict checking\.$`; `^Host key verification failed\.$` |
| `authenticationFailed` | `^(?:.+: )?Permission denied \([^()]+\)\.?$`; `: Too many authentication failures$`; `^No more authentication methods to try\.$` |
| `connectionRefused` | `^ssh(?:\.exe)?: connect to host .+ port [0-9]+: Connection refused$`; `^(?:kex\|ssh)_exchange_identification: `; `^banner exchange: `; `^Unable to negotiate with .+: no matching .+$`; `^channel 0: open failed: `; `^exec request failed on channel 0$` |
| `hostUnreachable` | `^ssh(?:\.exe)?: connect to host .+ port [0-9]+: .+$`; `^ssh(?:\.exe)?: Could not resolve hostname .+: .+$`; `^Connection timed out during banner exchange$` |
| `launchFailed` | `^Bad owner or permissions on .+$`; `: terminating, [0-9]+ bad configuration options?$`; `^command-line line [0-9]+: .+$`; `^Can't open user config file .+$`; `^Cannot execute command-line and remote command\.$` |

A client using an in-process ssh library derives the same outcome from its own
events. Before the exec request is written, a failure is `never`: name
resolution and no route give `hostUnreachable`, a refused socket, key exchange
and a refused session channel give `connectionRefused`, a rejected key gives
`authenticationFailed`, a host key gives `hostKeyChanged`/`hostKeyUnknown`. From
the moment the exec request is written, any failure is `linkLost`, `unknown`.
Once the channel completes, rows 2–10 apply with an empty log.

### 15.5 Walking attempts

Attempts are the routes in the order of section 10.3. For each route, the
systems whose effective agent (section 9.9) is non-empty come in this order: the
one its endpoint hint names, then the preferred system, then document order. No
client derives a launcher, interpreter or grammar. One deadline covers the whole
command (`status`: 30 s). For each attempt:

1. Skip a route that is backing off or has already failed with a route-level
   kind.
2. Once an attempt has been made, stop when less than 4000 ms remain.
3. `status` against an agent known to speak contract 3:
   `B = min(20000, remaining − 5000)` in whole milliseconds. When `B < 1000`,
   stop if an attempt was already made, otherwise use 1000. Send
   `--budget-ms B`. An agent not yet known to speak contract 3 gets no
   `--budget-ms`.
4. Run with a process timeout of the remaining time.
5. A reply ends the walk.
6. **A mutation is never attempted again, on any route or system, unless the
   failure was `never`.** A read continues after any failure.
7. After a route-level kind, skip the rest of that route's systems.

A mutation that stopped `unknown` or `acknowledged` is reconciled with
`op <id>`, never resent.

### 15.6 Addresses

`host` is an IPv4 dotted quad (octets 0–255 without leading zeros), an RFC 4291
IPv6 text address without brackets or zone, or a name of dot-separated labels
`[A-Za-z0-9_]([A-Za-z0-9_-]{0,61}[A-Za-z0-9_])?` of at most 253 characters whose
last label is not all digits. `user` is 1–64 characters from
`A-Z a-z 0-9 . _ - @ \` and space; it starts with a letter, digit or `_`, ends
with a letter, digit, `.`, `_` or `-`, and never has a space followed by a space
or `-`. `port` is an integer 1–65535. These apply to `endpoints[]` and the
deprecated `machine.ssh`, and also to the `hostname` and `hostkeyalias` that
`ssh -G` reports before a host key is pinned; when those fail, enrolment is
refused with "manual SSH enrollment needed". A client refuses to dial, scan or
pin any other value (`badRequest`, `never`) and says which entry it skipped
(section 9.7 `endpoint-undialable`). ssh always gets `-- user@host`,
`ssh-keyscan` always gets `-p PORT -- HOST`, and a pin pattern is `host` or
`[host]:port` built only from checked values.
